# Capture Independent Supervisor Evidence

<!-- regression-guard: not-applicable -->

## What & Why

Capture authentic registration/attestation and applicable evidence for an independent outer supervision route before any later FG-02 validation launch. Existing cooperative per-step supervision and historical fixed-bootstrap proof do not establish independent supervision for a new operation.

This is documentary capability intake only. It cannot register a supervisor, run readiness proof, or borrow source-stage approval/budget for validation.

## Done looks like

- A supported distinct outer supervisor/watchdog route and responsible evidence source are identified with versions and authorized read/export scope.
- Current registration/attestation binds the precise proposed future validation operation, real task/plan/source identity, selected registered tier or named bounded capability, command/selectors and complete transitive scope. If that future subject is not finalized, applicability remains BLOCKED.
- Evidence distinguishes the independent outer boundary from the supervised event loop, ordinary CLI availability, shell timeout, policy ceilings, local fixtures, leases and Agent defaults.
- Finite pre-dispatch, registration, queue, execution, startup/teardown, cancellation, termination verification and evidence limits, shared parent accounting, exact owned identities and evidence transport are documented from genuine sources.
- Available applicable host evidence for registration-before-dispatch, owner stall/death, watchdog loss, timeout/cancellation, complete owned-tree termination or quarantine, bounded capture and acknowledgement is assessed without new launches.
- Cooperative process-group or /proc limitations and uncontained local/remote escape paths remain explicit blockers. A fixture pass is not host attestation.
- Missing initial safety proof yields a scoped first-proof proposal and explicit blocker, not an uncontained launch or a demand that the proposed suite already passed. No prerequisite is claimed satisfied without actual applicable registration and evidence.

## Out of scope

Installing or registering supervisors/watchdogs; changing wrappers, callers, commands, policy, source files, workflows, services, shared dossiers or coordinator; starting fixture/health/proof workloads; signals or cleanup/reclaim; running CLI, imports, syntax checks, tests, builds or CI; issuing budget/approval; activation, cutover or deployment.

## Steps

1. **Separate the authority domains** — Read permitted host sources and establish the exact future validation subject separately from the source-stage operation. Identify existing outer-boundary mechanisms and their documented limitations without invoking them.
2. **Obtain authentic supervision evidence** — Locate the supported independent registration/attestation and evidence read route, using only specifically permitted records or exports. If unavailable, prepare the exact owner request without registering a replacement.
3. **Assess applicable coverage** — Map finite admission, parent/accounting, complete transitive ownership, cancellation/termination, bounded capture and acknowledgements to actual source-bound host evidence. Preserve unverified paths and fixture-versus-host distinctions.
4. **Publish a separate intake dossier** — Record FOUND/BLOCKED/UNKNOWN per capability with actual revisions and read permissions. Propose the smallest separately authorized integration/initial proof where needed, including a safe independent boundary before any proof launch; do not run it.

## Task identity and coordination

This platform task grants no local validation capability. Do not allocate IDs or modify registration records. Approval, budget and supervisor dossiers can be collected independently, but later use requires matching exact real subject/version and an independent decision to launch.

Write only this task's tracked report. Do not update the shared primary handoff or treat the other intake task's status as evidence. Source-stage approval is never validation, recovery or reclaim authority.

## Pre-existing failures to ignore

None authorized. Preserve unknown ownership, retained errors and historical proof limitations. Do not waive incidents, clear exclusion or infer termination from child exit.

## Validation

**Command:** None authorized; permitted bounded source/document readback only.
**Why:** A safe independently supervised first-proof route must be established before executing the very proof that would assess it.
**Do not escalate:** Unknown scope, missing independent supervision, registration/attestation, budget, capture or lifecycle evidence means BLOCKED. Availability of automated testing is not permission to launch it.

## Regression Guard

Not applicable to runtime behavior: documentation-only capability intake. Preserve existing independent callers and supervisor implementations without edits or tests.
